# PROXY_INTEGRATION.md

Contract between the **ImageShield proxy** (the existing `ImageShieldPhotoShare` backend) and the
**ImageShield services repo** (this one).

Mirrors the AgentMeeMaw `NODE_INTEGRATION.md` pattern. Read that first if you haven't — the shape is
deliberately the same so the two systems feel alike. Divergences are marked **⚠ DIFFERS FROM
AGENTMEEMAW** and each has a reason.

---

## 1. Repo split and ownership

```
┌──────────┐     ┌─────────────────────┐     ┌──────────────────────────┐
│ Mobile / │ ──▶ │ ImageShield Proxy   │ ──▶ │ ImageShield Services     │
│ Web      │     │ (existing backend)  │     │ (this repo)              │
└──────────┘     └────┬────────────────┘     └────┬─────────────────────┘
                      │                           │
                ┌─────┼──────┐          ┌─────────┼──────────┬──────────┐
                ▼     ▼      ▼          ▼         ▼          ▼          ▼
            DynamoDB  S3   Postgres  Postgres  Rekognition  Queues   Crop
             (proxy) (proxy) (read:   (write:               (pg)     Fetcher
                            reports)  all)                          (isolated)
```

### Proxy owns

- **Auth, sessions, OTP.** The proxy is the auth boundary. See §2 — and see the precondition, which
  is not currently met.
- User profile CRUD, household membership, invites.
- **Billing.** Stripe and Apple webhooks, subscription state, entitlement. `POST /stripeWebhook`
  already verifies its caller and stays where it is. Billing has exactly one owner at all times.
- FCM / push delivery.
- Minting presigned S3 URLs for client uploads.
- **All user-facing reads** of report data from Postgres, read-only. See §6.

### Services repo owns

- Identity: liveness sessions, consent records, enrolment, the Rekognition collection.
- Match: partner ingest, forward and backfill search, candidate emission.
- Adjudication: review queue, reviewer decisions.
- Report generation — all **writes** to `report_hits`, `reports`, `search_runs`.
- The crop fetcher (its own deployable, no VPC access).
- Every queue and worker.

### Hard rule — the client never talks to services directly

Every call goes **Client → Proxy → Services**. The services repo has no CORS surface, no public
ingress, and no per-user auth. Network topology enforces it: services live on a private subnet
reachable only from the proxy. Any client code that knows a service URL or a service token is a bug.

Holds in local dev, staging, and production without exception.

### Hard rules — the proxy MUST NOT

- Write to any identity table: `users`, `consent_records`, `liveness_sessions`, `enrolments`.
  Not even reads — see §6.
- Write to `report_hits`, `reports`, `match_candidates`, `search_runs`, `review_*`. Reads only, and
  only the columns in §6.
- Hold, proxy, cache, or log **face bytes**. Selfies go client → S3 via presigned URL, never through
  the proxy process. See §5.
- Call Rekognition. Any Rekognition API call from the proxy is a boundary violation.
- Enqueue onto any queue. The services repo produces and consumes all of them.
- Compute a likeness score. Scores are server-authoritative and generated by the report service.

If the client needs something the services repo doesn't expose, ask for an endpoint. Don't reach for
raw SQL.

## 2. Authentication

Same model as AgentMeeMaw: **no per-user auth between proxy and services.** Services trust the network
plus a shared service token. The proxy is the auth boundary — by the time a request arrives, the proxy
has authenticated the user and resolved a `user_id`.

### ⚠ PRECONDITION — not currently met

The AgentMeeMaw contract states: *"If the user is wrong, Node is wrong."* That is a safe premise there
because Node has working auth.

**The ImageShield proxy currently has none.** Per `docs/audit/AUTH-REALITY.md`: zero working
authenticated endpoints out of 154, no token ever issued, the client's `Authorization` interceptor
commented out, and the login OTP readable over HTTP via `GET /users/:phone`.

Therefore:

- Build the services repo now. Develop against `SERVICE_TOKEN_AUTH_DISABLED=1` locally.
- **Do not expose services to any environment carrying real user traffic until the proxy issues and
  verifies session tokens.** Until then, a services repo behind this proxy means biometric data behind
  a phone number in `localStorage`.
- The proxy's auth work is tracked as Phase 1 and is a hard gate on go-live, not on development.

### Tokens

| Token | Purpose | Required for |
|---|---|---|
| `SERVICE_TOKEN` | Service-to-service shared secret | Every endpoint except `/health` |
| `ADMIN_SERVICE_TOKEN` | Privileged / reviewer operations | `/admin/*` and `/review/*`, in addition to `SERVICE_TOKEN` |

Both set in the services environment. They **must be different values** — the service refuses to boot
if they match.

### Headers

```
X-Service-Token:        <SERVICE_TOKEN>
X-Admin-Service-Token:  <ADMIN_SERVICE_TOKEN>   # /admin/* and /review/* only
X-User-Id:              <uuid>                  # resolved by the proxy, required on user-scoped calls
X-Request-Id:           <uuid>                  # propagated end to end
X-Client:               ios/1.4.2 | android/… | web/…
```

Token comparison is constant-time. Mismatch or missing → `401`.

`X-User-Id` is a UUID, always. Never a phone number, never anything phone-derived. A request carrying
a phone number where a `user_id` belongs is rejected `400` — this is the guard against the old key
scheme leaking across the boundary.

### Sourcing

Both tokens live in the proxy's AWS Secrets Manager. Never in a client bundle, never in a response
body, never logged. Rotation is a coordinated deploy of both sides; there is no in-flight protocol.

`SERVICE_TOKEN_AUTH_DISABLED=1` is honoured for local dev only. Setting it in staging or production is
an incident.

## 3. Transport conventions

**Base URL:** `http://imageshield-services.internal:8080/v1`

JSON in, JSON out. `Content-Type: application/json`. All timestamps ISO 8601 UTC. All IDs are UUIDs.

### Timeouts

| Endpoint class | Proxy timeout |
|---|---|
| Identity reads | 3s |
| Liveness session create | 5s |
| Enrolment trigger | 10s |
| Report reads | 3s |
| Crop render | 8s |
| Admin / backfill trigger | 30s |

### Retries

Retry `5xx`, connection errors, and timeouts. Exponential backoff, jitter, max 3 attempts.

**Never retry** `4xx`. Never retry a liveness session creation — a retry mints a second session and the
first is consumed on the client, producing an enrolment that references a session the user never
completed.

All mutating endpoints accept `Idempotency-Key`, with one deliberate exception:
`POST /v1/liveness/sessions` **rejects** the header with `400` (CLAUDE.md §9). It creates a provider
session and burns a rate-limit attempt, so a caller must never be allowed to assume retrying it is
safe. `POST /v1/liveness/{sid}/result` **requires** the header: a same-key retry replays the stored
outcome; a different key against a completed session gets `410`.

### Errors

```json
{
  "error": {
    "code": "liveness_expired",
    "message": "Session expired. Ask the user to retry.",
    "retryable": false,
    "request_id": "…"
  }
}
```

`code` is a stable machine-readable string. The proxy maps codes to client-facing copy; it never
forwards `message` verbatim to a client, and never forwards `request_id` to a client either.

⚠ **DIFFERS FROM AGENTMEEMAW:** no ad-hoc status codes. The old backend uses `600` and `700` as error
signals. Standard HTTP only — `400`, `401`, `403`, `404`, `409`, `422`, `429`, `5xx`.

## 4. Endpoints the proxy calls

Full shapes in `docs/services/identity.md`. Summary:

| Endpoint | Purpose |
|---|---|
| `POST /v1/users` | Create identity record. Proxy supplies `phone_e164`, gets `user_id` |
| `GET /v1/users/{id}` | Enrolment + consent status. Never returns vectors or face IDs |
| `PATCH /v1/users/{id}` | Profile fields. Partial — absent fields untouched |
| `POST /v1/users/{id}/consent` | Render, hash, store, create DocuSeal submission. Takes `return_url` from the client |
| `POST /v1/liveness/sessions` | Create session (built, step 3). Returns `provider_session_id` for the client SDK. Rejects `Idempotency-Key` — see §3 |
| `POST /v1/liveness/{sid}/result` | Retrieve + persist the result, index on pass (built, steps 3–4). Requires `Idempotency-Key` and presigned PUT URLs. `enrolled: true` once `IndexFaces` succeeds; `passed` + `enrolled: false` + `reason: 'quality_rejected'` means the frame failed the HIGH quality gate — start a FRESH session. 503 (`face_index_unavailable`) means retry with the same key |
| `GET /v1/liveness/{sid}` | Read session status + `enrolled` (built, steps 3–4). Pure read — no side effects; enrolment is triggered by the result call |
| `POST /v1/users/{id}/enrolment/upload-url` | Presigned PUT for a selfie. See §5 |
| `DELETE /v1/enrolments/{user_ref}` | `DeleteFaces` → verify via `ListFaces` → tombstone (built, step 4). Idempotent 204; nothing calls it in v1. Full user deletion (`DELETE /v1/users/{id}`) remains specified-not-built — this is the enrolment-owning piece of it |
| `GET /v1/reports/{user_id}` | Report summary. Reads may go direct to Postgres instead — §6 |
| `GET /v1/hits/{hit_id}/crop` | Blurred face crop, streamed. `Cache-Control: no-store` |
| `POST /v1/admin/backfill` | Trigger a backfill run. Admin token required |

### Enrolment completion also signals via `NOTIFY`

A successful enrolment emits Postgres `NOTIFY enrolment_complete` with the `session_id` as payload,
inside the writing transaction (CLAUDE.md §9). Treat it as a wake-up only — read authoritative state
from the table; the synchronous result response already carries the same outcome.

### `return_url` is client-supplied

Mobile passes a deep link; web passes an https redirect. The services repo never hardcodes either.
This is what collapses the old `/api/consent/*` and `/api/web-consent/*` split into one path.

## 5. Face bytes never transit the proxy

⚠ **DIFFERS FROM AGENTMEEMAW** in the direction of the existing tribute/storybook pattern — the proxy
mints presigned URLs, the service does the work.

```
1. Client → Proxy:     POST /enrolment/upload-url
2. Proxy  → Services:  POST /v1/users/{id}/enrolment/upload-url
3. Services → Proxy:   { upload_url, object_key, expires_at }   (presigned PUT, 5 min)
4. Proxy  → Client:    { upload_url, object_key }
5. Client → S3:        PUT the selfie directly
6. Client → Proxy:     POST /enrolment/complete { object_key }
7. Proxy  → Services:  forwards; identity service reads from its own bucket
```

The bucket belongs to the identity service. The proxy has no read access. Object keys are UUID-derived
— never `<phone>.jpg`.

The proxy never base64s an image into a request body. The old `/upload-selfie` pattern does exactly
that and does not survive.

## 6. Postgres access from the proxy

⚠ **DIFFERS FROM AGENTMEEMAW:** narrower. AgentMeeMaw gives Node read access to the whole canonical
graph with a forbidden-column list. Here, access is per-schema and identity is entirely off-limits.

| Schema | Proxy access |
|---|---|
| `identity` | **None.** No role, no grant, no network path |
| `report` | `SELECT` on `reports`, `report_hits`, `hit_feedback` |
| `match` | **None** |
| `adjudication` | **None** |

Reasoning: identity holds Article 9 biometric data and the isolation is the point (INVARIANTS #14).
Report reads are high-volume and user-facing, so direct reads beat HTTP round-trips — that's the case
AgentMeeMaw's pattern is good for, and it applies here.

Proxy uses a distinct DB role with `SELECT` only on those three tables. Verify by attempting an
`INSERT` — it must fail with a permission error, not be caught by application logic.

### Columns the proxy must never surface to a client

- `report_hits.source_url` — only behind the interstitial copy action (INVARIANTS #22)
- `report_hits.face_bbox` — internal to crop rendering
- `report_hits.candidate_id`, `decision_id` — provenance, not user-facing
- Anything from `match` or `adjudication`

## 7. Queues

All queues are Postgres-backed (`graphile-worker` / `pg-boss`) and live in the services repo. Jobs are
enqueued in the same transaction as the row that triggers them.

| Queue | Producer | Consumer |
|---|---|---|
| `identity:index` | identity | identity |
| `match:forward` | ingest | match |
| `match:backfill` | identity (`identity.enrolled`) | match |

⚠ **DIFFERS FROM AGENTMEEMAW:** the proxy consumes nothing. In AgentMeeMaw, Node drains
`artifact_generation`. Here there is no equivalent — rendering is synchronous and request-scoped
through the crop fetcher, and the proxy has no worker role.

Notifications: the report service writes digest rows; the proxy polls or receives a webhook and
delivers via FCM. The proxy owns delivery, the services repo owns content and cadence — including the
22:00–08:00 quiet window (INVARIANTS #24), which is enforced service-side so a proxy bug can't wake
someone at 2am.

## 8. Local development

```bash
docker compose -f docker-compose.local.yml up
```

Brings up identity, main app, crop fetcher, and Postgres. `SERVICE_TOKEN_AUTH_DISABLED=1` is set in
`.env.local` and nowhere else.

Rekognition is stubbed by default (`REKOGNITION_STUB=1`) — liveness always passes, `IndexFaces`
returns a deterministic fake face ID. Set `REKOGNITION_STUB=0` with real credentials to exercise the
real path. **Never point local dev at the production collection.**

The crop fetcher runs against a local fixture server, not live URLs.

## 9. What this contract does not cover yet

- **The partner ingest interface.** Blocked on knowing which embedding model produces their vectors.
  Until answered, `match:forward` has no defined payload and the match service can't be built.
- **Reviewer tooling auth.** Reviewers are not users; they need their own identity model. Currently
  covered only by `ADMIN_SERVICE_TOKEN`, which is not sufficient for an audit trail naming an
  individual reviewer.
- **Proxy → services observability.** Request ID propagation is specified; distributed tracing is not.
